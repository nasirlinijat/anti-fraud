# Testing

## Running tests

Services and handlers have unit tests that need no database. Their dependencies are replaced with mocks generated by [gomock](https://github.com/uber-go/mock):

```bash
cd backend
go test ./internal/services/... ./internal/transport/...
```

Every store interface in `internal/services/*` and every service interface in `internal/transport` has a `//go:generate mockgen` line. The generated code is in a `mocks` folder next to it and is committed. After changing one of these interfaces, regenerate the mocks:

```bash
go install go.uber.org/mock/mockgen@v0.6.0
cd backend
go generate ./internal/...
```

Tests that read or write the database are skipped unless `TEST_DATABASE_URL` is set; `make test` sets it and runs them all.

The integration tests in `backend/test/integration` run the API the way `cmd/api/routes.go` wires it, against a real PostgreSQL, as the restricted `antifraud_api` role. They start their own PostgreSQL 18 in Docker with [Testcontainers](https://golang.testcontainers.org/), apply every migration and `runtime-role.sql`, so they need only Docker running:

```bash
cd backend
go test -tags=integration ./test/integration/...
```

To use an existing, migrated database instead, set `TEST_DATABASE_URL`, and `TEST_RUNTIME_DATABASE_URL` for the role checks.

The concurrency tests in `backend/test/concurrency` send requests at the same moment to a real HTTP server and check that the database stays correct: 20 scores of one transaction save one decision, 10 ruleset publishes leave one active version with consecutive numbers, two reviewers deciding a claimed review save one decision, and two analysts sending batch decisions over overlapping purchases save one decision per purchase, with one `saved` result and one `not_claimed` or `already_decided` result for each shared purchase. They always start their own PostgreSQL, because they commit data and change the active ruleset. CI runs them with the race detector:

```bash
cd backend
go test -race -tags=integration ./test/concurrency/...
```

The concurrency suite also holds review changes uncommitted while competing requests arrive. It verifies both decision/release orderings, competing claims, and release followed by a new claim, using the restricted API role for the waiting requests.

`make test-integration` runs both folders one after the other (`go test -p 1 -tags=integration ./test/...`).

## Clean demo start

Ask a teammate who did not write the change to start from a fresh checkout. With Docker already running and the README prerequisites installed, use a fresh Compose project with an empty volume. Start a timer before copying `.env.example`, follow the [quick start and demo seed instructions](../../README.md#quick-start), and stop the timer when an admin can sign in and see the populated dashboard and review queue. Record the elapsed time, whether it was under 10 minutes, and any corrections needed in the README.

For repeatability, run `make seed` twice with the same model and ruleset. Compare **All time** outcomes, blocked value, top rules, model effects, and open reviews. The default demo should leave 10 open reviews. Scoring latency, timestamps, and generated database IDs vary by run.

## Scoring load test

Run this from the repository root with a local Docker engine, Go, Python 3, and curl:

```bash
./scripts/scorebench.sh
```

The script builds the API image and starts a disposable PostgreSQL 18 instance and API on loopback ports. It applies the migrations, loads 500,000 synthetic purchases and matching decisions spanning 120 days, and initializes all six feature-count groups. The API uses the restricted database role. An admin session publishes ruleset version 2 with the seeded settings plus device card count and new device spike enabled, preserving the model settings in assist mode. Scoring uses the service key and the Compose model, `lgbm-ieee-v5-combined`.

Seed 42 selects returning players, cards, and devices for 100 warm-up requests and 1,000 timed requests. The timed mix is 800 routine purchases, 100 on shared devices, and 100 large purchases on unseen devices. Across those groups, 100 requests have a missing issuer and 100 use a common issuer. The client sends one request at a time in event order and measures through the end of the HTTP response body. The script checks that the timed decisions were saved, verifies both new rules fired, and requires p95 below 50 ms. It removes the benchmark containers, database volume, and network at exit.

### Local results

Measured on November 11, 2026, on an Apple M4 with 10 CPU cores and 16 GiB RAM, macOS 26.6.2, Docker Engine 29.8.1 with 10 CPUs and 7.75 GiB allocated, and PostgreSQL 18.6. The baseline used `99d3398`. The covering-index change first reduced p95 to 40.76 ms and 39.21 ms on that same base. The final runs below include `main` at `35cc6c5`, migration `000020`, the restricted API database role, and operator authentication.

| Run | HTTP p50 | HTTP p95 | HTTP p99 |
|---|---:|---:|---:|
| Baseline | 19.05 ms | 94.13 ms | 121.46 ms |
| Final 1 | 7.25 ms | 38.37 ms | 40.57 ms |
| Final 2 | 8.27 ms | 41.39 ms | 66.62 ms |

Both final runs saved all 1,000 decisions. Each new rule fired 100 times per run. `pg_stat_statements` ranked issuer history first by mean and total execution time. Its mean was 28.09 ms in the baseline and 10.30 ms and 11.47 ms in the final runs. `EXPLAIN (ANALYZE, BUFFERS)` showed index-only scans for the typical, missing, and common issuer samples. The player, card, model history, device-card count, and trusted-purchase history plans used their indexes with no sequential scans. The issuer query still counts distinct values across both indexes. Rows with wide text use the index with the original keys.

## Console sessions

`cd frontend && npm run test:browser -- e2e/auth.spec.ts` checks login, roles, accounts, assignments, idle session expiry, focus revalidation, temporary verification outages, and a delayed logout after another tab replaces the session across Chromium, Firefox and WebKit. Request tests cover obsolete and cancelled responses; the local proxy test verifies scoring is never forwarded when session verification fails.

The linked-review accessibility checks in `e2e/console.spec.ts` initialize light and dark mode in separate browser contexts before opening the case. Each checks selected and unselected purchases at desktop and mobile widths, after verifying the rendered color scheme. This keeps the contrast audit from sampling colors during a live theme change; live system-preference changes are covered in `e2e/theme.spec.ts`.
