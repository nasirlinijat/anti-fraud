# Testing

From `backend`, run `go test -tags=integration ./test/integration -run '^TestSeededSimulationAnswerDemo$' -v` for the simulator answer demo. The test starts a disposable PostgreSQL database with the runtime and evaluation roles and scores 20 generated purchases from seed 42. It uses seeded ruleset v1, the model off, and empty purchase history, then checks for at least one missed fraud and one legitimate purchase flagged by scoring.

## Running tests

Services and handlers have unit tests that need no database. Their dependencies are replaced with mocks generated by [gomock](https://github.com/uber-go/mock):

```bash
cd backend
go test ./internal/services/... ./internal/transport/...
```

Every store interface in `internal/services/*` and every service interface in `internal/transport` has a `//go:generate mockgen` line. The generated code is in a `mocks` folder next to it and is committed. After changing one of these interfaces, regenerate the mocks:

```bash
go install go.uber.org/mock/mockgen@v0.6.0
cd backend
go generate ./internal/...
```

Tests that read or write the database are skipped unless `TEST_DATABASE_URL` is set; `make test` sets it and runs them all.

The integration tests in `backend/test/integration` run the API the way `cmd/api/routes.go` wires it, against a real PostgreSQL, as the restricted `antifraud_api` role. They start their own PostgreSQL 18 in Docker with [Testcontainers](https://golang.testcontainers.org/), apply every migration and `runtime-role.sql`, so they need only Docker running:

```bash
cd backend
go test -tags=integration ./test/integration/...
```

To use an existing, migrated database instead, set `TEST_DATABASE_URL`, and `TEST_RUNTIME_DATABASE_URL` for the role checks.

The concurrency tests in `backend/test/concurrency` send requests at the same moment to a real HTTP server and check that the database stays correct: 20 scores of one transaction save one decision, 10 ruleset publishes leave one active version with consecutive numbers, two reviewers deciding a claimed review save one decision, and two analysts sending batch decisions over overlapping purchases save one decision per purchase, with one `saved` result and one `not_claimed` or `already_decided` result for each shared purchase. They always start their own PostgreSQL, because they commit data and change the active ruleset. CI runs them with the race detector:

```bash
cd backend
go test -race -tags=integration ./test/concurrency/...
```

The concurrency suite also holds review changes uncommitted while competing requests arrive. It verifies both decision/release orderings, competing claims, and release followed by a new claim, using the restricted API role for the waiting requests.

`make test-integration` runs both folders one after the other (`go test -p 1 -tags=integration ./test/...`).

## Authentication fixtures

Transport session fixtures seed separate accounts in each test transaction using
one immutable cost-12 hash of the fixture password. Each account still signs in
through the real authentication service; account-creation requests and dedicated
password, session, expiry, disabled-account and role tests retain their real paths.
Only the hash is shared across tests, never accounts or session tokens.

The tagged integration app creates and signs in its admin/reviewer lazily, then
reuses that session within the app transaction. Cached sessions are never refreshed
automatically after logout or account disable. Explicit reviewer sign-ins remain
explicit. Single-review decisions still prepare their claim on every request.
Fixture regressions cover one session per role, authorization, revocation and
isolation after rollback. All database state is discarded with the transaction.

## Scoring load test

Run this from the repository root with a local Docker engine, Go, Python 3, and curl:

```bash
./scripts/scorebench.sh
```

The script builds the API image and starts a disposable PostgreSQL 18 instance and API on loopback ports. It applies the migrations, loads 500,000 synthetic purchases and matching decisions spanning 120 days, and initializes all six feature-count groups. The API uses the restricted database role. An admin session publishes ruleset version 2 with the seeded settings plus device card count and new device spike enabled, preserving the model settings in assist mode. Scoring uses the service key and the Compose model, `lgbm-ieee-v5-combined`.

Seed 42 selects returning players, cards, and devices for 100 warm-up requests and 1,000 timed requests. The timed mix is 800 routine purchases, 100 on shared devices, and 100 large purchases on unseen devices. Across those groups, 100 requests have a missing issuer and 100 use a common issuer. The client sends one request at a time in event order and measures through the end of the HTTP response body. The script checks that the timed decisions were saved, verifies both new rules fired, and requires p95 below 50 ms. It removes the benchmark containers, database volume, and network at exit.

### Local results

Measured on November 11, 2026, on an Apple M4 with 10 CPU cores and 16 GiB RAM, macOS 26.6.2, Docker Engine 29.8.1 with 10 CPUs and 7.75 GiB allocated, and PostgreSQL 18.6. The baseline used `99d3398`. The covering-index change first reduced p95 to 40.76 ms and 39.21 ms on that same base. The final runs below include `main` at `35cc6c5`, migration `000020`, the restricted API database role, and operator authentication.

| Run | HTTP p50 | HTTP p95 | HTTP p99 |
|---|---:|---:|---:|
| Baseline | 19.05 ms | 94.13 ms | 121.46 ms |
| Final 1 | 7.25 ms | 38.37 ms | 40.57 ms |
| Final 2 | 8.27 ms | 41.39 ms | 66.62 ms |

Both final runs saved all 1,000 decisions. Each new rule fired 100 times per run. `pg_stat_statements` ranked issuer history first by mean and total execution time. Its mean was 28.09 ms in the baseline and 10.30 ms and 11.47 ms in the final runs. `EXPLAIN (ANALYZE, BUFFERS)` showed index-only scans for the typical, missing, and common issuer samples. The player, card, model history, device-card count, and trusted-purchase history plans used their indexes with no sequential scans. The issuer query still counts distinct values across both indexes. Rows with wide text use the index with the original keys.

## Parallel backend CI and coverage

CI runs two regular-test shards and the complete tagged suite independently.
The `cpu` shard owns exactly `internal/lgbm` and `internal/simulator`; `core`
receives every other package from unfiltered `go list ./...`, including packages
without tests. Newly added packages automatically enter core. Both regular
shards get private PostgreSQL/Redis services, all migrations and runtime/labels
roles. Packages within a shard remain serial (`-p 1`). All test commands retain
race detection and use `-count=1` so build caches cannot replace stateful tests.
The tagged job runs all of `./test/...`, including reset tests, with database
variables empty so Testcontainers owns its services.

The existing `CI / backend` check is the final gate: failed, cancelled, skipped
or missing prerequisites cannot pass it. Only the regular suites contribute to
the existing `backend-coverage` report. Raw zero-hit statements are retained;
only the existing `/mocks/` exclusion is applied to the final reports.
Shard artifacts have unique names (`backend-coverage-core` and
`backend-coverage-cpu`) and contain `coverage.out`, `tests.jsonl` and a versioned
`manifest.json`. The manifest identifies the checkout, Go version, exact package
assignment and profile checksum. Aggregation rejects incomplete/mismatched
artifacts, non-atomic profiles, duplicate blocks or wrong package ownership.
Download those artifacts by exact name; Docker build-record artifacts are not
coverage inputs.

Run the helper tests from the repository root:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/ci -p 'test_*.py'
```

For local equivalents, provision separate migrated PostgreSQL and Redis instances
for each concurrent shard. Set TEST_DATABASE_URL, TEST_RUNTIME_DATABASE_URL,
TEST_LABELS_DATABASE_URL and TEST_REDIS_URL for each process. From the root:

```bash
python3 scripts/ci/backend_checks.py run --shard core --output-dir /tmp/ci-core
python3 scripts/ci/backend_checks.py run --shard cpu --output-dir /tmp/ci-cpu
python3 scripts/ci/backend_checks.py merge --core /tmp/ci-core --cpu /tmp/ci-cpu --output-dir /tmp/ci-merged
```

The regular shard commands may run concurrently only with independent services.
For the tagged job, from backend, unset all four TEST_ connection variables and
run `go test -race -count=1 -p 1 -tags=integration ./test/...`.

Before changing shard assignments, capture a reference from the same Go source,
toolchain and platform with fresh equivalent services:
`go test -json -race -count=1 -p 1 -covermode=atomic -coverprofile=/tmp/ci-reference.out ./...`.
Compare it with the combined raw profile using:

```bash
python3 scripts/ci/backend_checks.py compare --reference /tmp/ci-reference.out --candidate /tmp/ci-merged/coverage.out
```

Block coordinates and statement totals must match exactly; positive hit counts
may differ, but losing a covered block fails comparison. Investigate only affected
packages with three fresh runs per topology if timing-dependent differences
occur. Do not weaken the check with a percentage tolerance. A profile comparison
is valid only for identical Go source, toolchain and platform; old profiles are
not a baseline for newly added tests. Compare package/test inventories too.

Go caches remain dependency/build caches. In Docker workflows, Images is the
only GHA layer-cache writer. Image scanning and Helm restore component caches,
load local single-platform images, and still execute every scan/smoke check.
Cache misses perform complete builds. Browser installation uses Chromium's
headless shell; the Chromium project, two CI workers and assertions are unchanged.
